# 发布说明

每一版一个文件：`<版本号>.md`（如 `0.4.3.md`），写**这一版对用户是什么**。

它会去三个地方，用户在这三处读到的是同一段话：

| 去处 | 怎么到的 |
|---|---|
| GitHub Release | `scripts/release.mjs` 发版时：`# 标题` 当 Release 标题，其余当正文 |
| 官网更新日志（narracat.com/changelog） | 官网每 10 分钟同步 GitHub Release，**标题、正文原样搬运**，后台审核后公开 |
| 发版确认界面 | 按下确认前原样打出来，最后看一眼 |

所以格式就是官网的格式：版本号 + 日期（自动）→ 主题标题 → 一句导语 → 新增 / 改进 / 修复 / 备注。

## 格式

```markdown
# 重写不再清后文

这一版修好了重写章节的几个老问题，并加上网络代理设置。

## 新增

- 设置里可以填网络代理，访问海外模型服务不用再改系统设置

## 改进

- 同一种失败连续 3 次会自动停下，不再白白消耗额度

## 修复

- 重写中间某一章，不再清掉后面各章的记忆和进度

## 备注

- 已受影响的书，这一版不会自动修复
- 感谢 @某某 的报告
```

| 部分 | 写什么 | 硬规则（不符合发不出去） |
|---|---|---|
| `# 标题` | 这一版的主题，像一句话的新闻标题：「Windows 版来了」「写作过程少踩坑」 | 第一行必须是 `# 标题` |
| 导语 | 一句话说清这一版对用户是什么 | 标题下必须有，只写一段 |
| `## 新增` | 以前没有、现在能做的事 | 分块只能是这四个，按这个顺序，不重复 |
| `## 改进` | 以前就能做、现在更好用 / 更快 / 更稳 | 每条一行 `- 条目`，不跨行 |
| `## 修复` | 以前坏了、现在好了 | 没内容的块整块删掉 |
| `## 备注` | 用户要知道但不算变化的事：已受影响的数据不会自动修、升级前要备份、运行要求、致谢 | 新增 / 改进 / 修复 至少有一块 |

**不用自己写**：自动更新怎么生效、首次安装下哪个文件、Windows 未签名怎么放行——发版脚本每次自动补在「备注」末尾。

## 怎么写得短

参考尺度（超了预检会提醒，不拦）：标题 16 字内，导语 60 字内，每条 50 字内。

- **一条 = 一个用户能感觉到的变化**。写「现在怎样」，必要时用半句交代「以前怎样」，不写根因和实现
- **用界面上的叫法**：「设置 → 模型服务」「作品页」「重写」。不写开发词：根因、归一、工具名、schema、MCP、run、CI、提交号
- **不加粗、不嵌套、不贴链接堆**；数字只写测得出来的（「3 次」可以，「快 43%」没测过就别写）
- **同类合并**：五条模型目录更新是一条「模型目录更新：新增 A、B、C」
- **不是用户感知的就不写**：重构、测试、文档、发版脚本、匿名统计的内部字段
- **分不清放哪块时**：用户以前能不能做这件事？不能 → 新增；能但不好 → 改进；能但坏了 → 修复

| 反例 | 改成 |
|---|---|
| `- **走中转网关、或用较弱模型时，Agent 读不了、写不了文件**：症状是…根因是模型照说明书写出的工具名和运行时登记的名字对不上，现在由 App 统一归一` | `- 走第三方中转渠道时，Agent 不再报「工具不存在」、读写不了文件` |
| `- 修复 GLM / Kimi 等渠道写正文一直被截断：输出上限按模型抬高，「设置 → 模型服务」里每个模型可以自己填；被截断时自动重试一次` | 拆两条：修复 `- GLM、Kimi 等渠道写正文不再被截断`；新增 `- 「设置 → 模型服务」里每个模型可以自己填输出上限` |

## 检查与预览

```bash
node scripts/release-notes.mjs 0.4.3 --windows   # 打印会发出去的标题与正文，附问题与提示
```

发版预检（release-app 技能）会报同样的问题；`release.mjs` 在打包前也会拦结构错误，免得白等签名与公证。
`scripts/release-notes.test.mjs` 让本目录每个历史文件都过同一套格式。

## 不写会怎样

不阻断发版——紧急修复可能真没什么好说的。但预检会出一条 `!` 提醒，Release 标题退回「NarraCat x.y.z」，
正文只剩「备注」里的通用样板，答不了「这一版改了什么」。

## 改历史版本

官网同步的是 GitHub 上的内容，改了这里的文件**不会**自己生效：

1. 改文件，走 PR 合进 main
2. 用 `node scripts/release-notes.mjs <版本号> [--windows]` 渲染，`gh release edit v<版本号> --title … --notes-file …` 改 GitHub
3. 官网后台 `/admin/changelog`：已人工校正过的条目不会被同步覆盖——在「来源变化」里点「采用来源正文」、标题照新的改，再发布

## 为什么会有这套东西

0.3.1 那次，CI 建 draft 时写的内部占位串被当成发布说明发给了所有用户，
连「Windows 未签名会撞 SmartScreen」那段必要告知都一起丢了。当时测试绿、CI 绿、产物齐全、
更新链两端 200——**四条判据全对，发出去的东西对用户仍然是不像样的**。于是有了这个目录。

2026-10 官网更新日志改为同步 GitHub Release 后，这段话也成了官网的门面。此前各版写法不一
（加粗小标题、根因长句、没有分块），于是定了这套与官网旧版一致的格式，历史版本一并回改。
