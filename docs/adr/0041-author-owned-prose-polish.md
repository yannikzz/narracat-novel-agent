# ADR 0041: 作者自持的正文润色通道（非 Agent 直连大模型）

## Status

Accepted（在 [0029](0029-two-tier-editing-direct-vs-agent-cascade.md) /
[0031](0031-manuscript-editing-save-first-two-tier.md) 的两档编辑框架内新增第三种正文
写入来源；不改引擎契约，`agent-core/` 零改动）

## Context

产品直出的正文「AI 味」仍重。2026-07-27 我们自己跑过一次成品润色实验（3 策略 × 2 模型
= 12 臂，机械校验全过），作者盲读的裁决是「基本没差别，AI 味依旧重」，并点名两个症状：
奇怪的比喻、上下文不连贯——二者都是**生成层**病灶，句子级润色救不动。

所以本 ADR **不是**在重跑那个已被证伪的方案。它换了一个立论：作者想自己动手改文字风格
时，手上没有任何工具——要么接受 Agent 写出来的样子，要么整章手敲。缺的是**通道**，不是
更好的配方。

## Decision

### 1. 定位：自主权工具，不承诺效果

产品**只提供通道**（直连大模型 + 作者自带提示词 + 三版横向对比 + 采用 + 可回退），
**不承诺润色能提升质量**，因此**出厂不携带任何风格模板或推荐提示词**——内置模板等于
效果背书，锅会回到产品身上，与本 ADR 的立论直接冲突。

### 2. 责任边界：账房归我们，花归用户

对齐北极星（[0030](0030-north-star-v2-substrate-capability-evaluation.md)）。该边界在
两个位置以同一形态落地，**不得单独破例**：

| 位置 | 我们给 | 我们不给 |
|---|---|---|
| 喂给模型的输入 | 本章人名 / 专名 / 数字清单 +「原样保留」 | 任何写法指令（风格档位、前章、立项卡） |
| 给作者的空槽引导 | 提示词骨架三行（要它做什么 / 不要它做什么 / 必须保留什么） | 骨架里填什么 |

**不喂完整上下文包**是刻意的：一旦注入风格指令，就等于产品在教模型怎么写，效果不好时
责任重新回到产品，且会与作者提示词打架。

### 3. 不经 Agent：走直连 Messages API

复用角色聊天已建成的直连链路（`chat/character-chat-runner` 的 keytar 取密钥 → Anthropic
Messages API），**不经 pi runtime、不消耗 Agent 能力、不进 Agent 会话**。

**v1 仅支持 `anthropic` wire**（与角色聊天现状一致）。模型池里 `openai` wire 的自定义
渠道在槽位下拉中**灰显并注明原因**，不静默消失。补 `openai` wire 应作为一次独立改动同时
惠及角色聊天与润色，不在本功能内做半条。

### 4. 位置：记忆入库之后，App 层追加（引擎零改动）

`/narracat:write` 的步骤 6 中 `novel_update_progress` 会先核对交付合同、再把草稿区正文
原子搬进正式路径——正文落地与记忆入库是同一步。润色**发生在整条写作命令跑完之后**，由
App 层追加，因此：

- 记忆抽取的永远是**未润色的原始版**；
- 润色改坏文字的爆炸半径被封死在**正文文字层**，事实、上下文包、角色状态不受污染；
- 引擎命令、Agent、Skill **一个字都不改**。

代价是「记忆里存的摘要基于原始版」。在纯文字润色下该代价为零（事实没变，摘要就没变）；
作者用提示词大改情节时，代价由第 6 条的分档处置承担。

### 5. 护栏：事实漂移判据，与既有 diff 分诊分离

**不复用 `manuscript-triage.ts`**。那套三信号（实体名出现 / 整段增删 / 变更字符 > 200）
是为「人手改几句话」设计的，用在整章重述上 100% 命中 → 每章一个红点 → 假警报训练作者
无视红点 → 真出事那次也被无视，等于废掉 0031 的第二档闸。

润色专用判据按**集合比对**（判「改了什么」而非「改了多少」）：

| 信号 | 判定 |
|---|---|
| 已知专名（角色名 / 别名 / 伏笔关键词）的出现集合变化 | 事实漂移。**闭世界比对**：清单之外凭空造出的新人名抓不到，见外审修复表 |
| 数字集合变化 | 事实漂移 |
| 段落数变化超阈值 | 事实漂移 |
| 仅句子、用词、语序变化 | 纯文字层 |

依据：2026-07-27 实验的机械校验（人名 / 数字 / 字数 / 段落不变式）12 臂全过，逻辑已验证。

### 6. 漂移处置按「此刻有没有人在读」分档

| 场景 | 处置 |
|---|---|
| 试验模式（作者正在读三版） | **放行**，每版顶部标注漂移明细。漂移信息是决策依据，不是错误——作者可能就是要一套敢改情节的配方 |
| 常驻模式（自动，无人看） | **跳过本章润色、保留原稿、可见告知**。常驻的前提是该配方已在试验阶段验证过，突发漂移即异常，默认保守 |

常驻模式因此只有两种结局：**润好了覆盖**，或**原稿原封不动**，永不出现半成品。跳过必须
可见（静默跳过会重演 gitignored 产物掩盖断链那类「坏了两周没人知道」）。

### 7. 记忆闭环三分支：正文可以不等于发布稿

产品里的正文**不一定是作者最终投递到发布平台的稿子**。作者拿旧章润一版用于导出 / 投稿，
与「让这次改动进入后续创作」是两件不同的事。因此**任意已完成章都可润**，不锁定最新章：

| 情形 | 处理 |
|---|---|
| 无漂移（绝大多数） | 直接采用，记忆不动，不打红点 |
| 漂移 + 最新完成章 | 采用 + 打 `pending-memory-sync` 标记 → 走 `/narracat:sync-chapter-memory` |
| 漂移 + 旧章 | **一次性确认**告知正文与记忆将分家 → 采用 → 该章挂**纯陈述标识** |

**旧章漂移采用后正文与记忆永久分家**，这是清醒接受的后果：`/sync-chapter-memory` v1 不
收旧章（0031 第 2 条），而 `/narracat:rewrite` 会重新生成正文、抹掉作者刚润出的版本，
**因此它也不是出口**。该标识**不配任何按钮**——真的没有正确操作可给，给一个按不下去的
按钮比不给更伤。

### 8. 试验 → 常驻 两阶段

| | 试验模式 | 常驻模式 |
|---|---|---|
| 触发 | 章节正文页 icon 按钮，手动 | 写完新章后 App 自动追加 |
| 跑几版 | 勾选本轮参与的槽（1-3），默认沿用上次组合 | 常驻那一槽 |
| 呈现 | 配置在弹窗、**结果回工作台正文区**：章节视图 tab 之下一行版本 tab（原稿 / 方案一二三），单版沉浸 + 对照原稿 diff 开关，流式渲染 | 无界面 |
| 落地 | 选中即采用，未选版本丢弃 | 自动覆盖，顶部横条可退回原稿 |

- **界面分两处，刻意不做成抽屉**：抽屉会把要读的正文整个盖住，等于让作者隔着一层看自己的书。
  配置（三槽横版并排 + 「开始润色」主按钮）用弹窗，跑起来即关；版本回到正文区，与章节视图 tab
  同一套视觉语言——判断润色好坏靠「读起来顺不顺」，那需要在他平时读这本书的地方整章读。
  事件订阅与版本生命周期因此挂在正文视图上，不挂弹窗：弹窗一关就断订阅，跑到一半的版本会永远
  停在「排队中」。
- **自动覆盖是安全的**，因为记忆入库的是原始版（第 4 条），且 `manuscript-revisions.ts`
  已是现成时光机（gzip 全文 + before/after 哈希），退回原稿是既有能力。
- **不做「双版长期并存」**：会让「正文是哪一版」这个本该唯一的事实变成处处要问的分支。
- **常驻只作用于往后新写的章**，不追溯已有章节。
- 固化入口两处（采用时顺势提议，**默认不勾**；润色弹窗随时可改可关），读写同一字段。
- **提议一本书只问一次**：已常驻不问，答过「这次就好」也不再问——那是一个明确的回答，
  不是「下次再问我」。每采用一版就弹一次，等于拿一个已被回答的问题反复打断作者。
  想改主意随时能在润色弹窗里改。

### 9. 配方 = 提示词 + 模型；存储分两层

**固定三槽，不可增删**（三是对比上限，也是界面的天然形状；可增删列表会被加到十个然后
没法对比）。每槽自带模型选择，**默认继承主力槽**。

槽位自带模型是为了让作者能分辨「是我提示词烂」还是「是这模型不行」——只能试第一个方向
的作者，最终结论会是「你们这功能没用」，锅又回到产品。润色是单次调用，成本量级远低于
写章链路，负担得起。

| 数据 | 存储位置 | 理由 |
|---|---|---|
| 三槽配方（提示词 + 模型） | `userData/polish-recipes.json` | 配方是作者的**手艺**，跨书复用 |
| 本书常驻槽位 | 项目内 `.narracat/` | 常驻是**这本书的决定** |

两者生命周期不同，焊死在任一层都会在另一头出问题（全局 → 古言与都市共用配方串味；
全项目 → 换本书手艺带不过去）。

### 10. 流式只服务试验模式

润色的流式**不是**为了边流边读（判断「整章顺不顺」需要完整文本，diff 与护栏也必须等
全文到齐才算得出）。

**推理模式是每槽的开关，默认关。** 关掉是默认值而不是唯一选项：对「重写这一段的逻辑」这类
要求，想一想确实可能更好，所以开关交给作者，产品负责在开启时把预算分好（思考预算从
`max_tokens` 里切，故开启时同步抬高总额，保证正文额度不变）。

⚠️ **实测提醒**：deepseek 的两个模型在开启推理后都会把整个额度烧在思考上、正文零产出
（flash：给足 8000 思考预算仍烧光 24000，跑 222 秒 `stop_reason=max_tokens`）。因此撞上限时
的报错**按是否开了推理分成两句**，不能混成「这一章太长」——两种情况的处置完全不同。

⚠️ **必须默认关掉扩展思考**（真机根因，2026-09-02，deepseek-v4-flash 经 anthropic 端点）：
该渠道默认开着 thinking，而 **thinking token 与正文共用同一个 `max_tokens` 预算**。实测一次
整章润色收到 `thinking_delta × 15994`、`text_delta × 0`——16000 的预算被思考烧光，
`content_block` 只开了思考那一个，跑满 128 秒零产出。**且这是随机的**：另一次同样的请求只想
了 10 下就动笔，所以偶尔能成，表现为「时灵时不灵」。关掉后连跑三次：0 个 thinking delta、
约 2350 个文本 delta、**首字 1.4 秒、总耗时约 14 秒**。润色是改写不是推理，思考零收益却吃掉
整章预算，没有保留的理由。

**⚠️ 本节初稿据此写过一条错误结论**（「该端点基本不做增量流式，首字要等 89 秒」）——那个 89 秒
正是 thinking 在烧预算，不是端点不流。**同一份现象在拿到根因前不要写进 ADR 当事实**。

两条产品要求仍然成立，与上面的根因无关：

1. **「它在干活的证据」不能只靠第一个字**。「还没收到第一个字」不等于「排队中」——请求早发
   出去了。界面显示每秒走动的「正在生成…已等 12 秒」。
2. **必须有硬超时**（6 分钟，正常一版约 15 秒）。没有它，「模型在那边空转」与「真的挂了」
   观感完全一致。超时报「没跑成」并说清原因，**不报「已中止」**——作者没按中止，不能栽给他。

另有一条硬性拦截：**`stop_reason === 'max_tokens'` 一律判失败**，不把截断的半章交给作者采用
——作者读到的是完整一章，采用后结尾会被悄悄吃掉。

### 「跑完和原文差不多」是常态，产品的答案是把改动量摆出来

真机第一次跑完，作者的反馈是「感觉和原文一模一样」。同一章跑对照实验（段落级原样比例）：

| 模型 | 措辞 | 思考 | 原样段落 |
|---|---|---|---|
| flash | 现状 | 关 | 83% |
| flash | 现状（**去掉「不许动」段**） | 关 | 82% |
| flash | 「重写」措辞 | 关 | 94%（更差） |
| pro | 现状 | 关 | **100%（完全照抄）** |
| pro | 「重写」措辞 | 关 | 82% |

三条结论：**①不是我们的锚清单造成的**（去掉它 83%→82%，无差别）；**②任务措辞不要动**——
把「加工」改成「重写」并补一句「剧情保持不变」，在 flash 上反而从 17% 改动掉到 6%
（再次印证「减法指令的服从度远高于加法指令」）；**③模型选择的影响远大于措辞**，pro 在现状
措辞下是纯复印机。

所以「改得少」的杠杆在作者的提示词和模型选择上，这正是本 ADR 的定位所指。产品该做的不是替他
调，而是**把改动量摆到他眼前**：每版状态显示「改动 N% 段落」。一版几乎没动时，沉浸读完只会
觉得「好像还行」，而他真正需要知道的是「我的要求根本没落地」——这个数让他不必读三千字就能
判断要不要改提示词。

- 流式渲染在**版本 tab 内**，不是原地覆盖正文——采用之前磁盘上一个字节都没变。
- 版本归属由 **`projectPath + chapter`** 共同判定：只判章号会让另一本书的同章号显示上一本的
  版本，而采用时用的是当前书的正文当乐观锁基线——那会把别的书的文字写进这本书。
- 版本只活在内存里（本次会话），**但不随离开页面消失**：只有作者点「丢弃」、采用了某一版、
  或发起新一轮时才清空。曾经挂在组件卸载上清，本意是「切章即丢弃」，实际是「离开这一页就丢」，
  切去看一眼章节大纲再回来，刚花十几秒跑出来的三版就没了。切章由 `polishChapter === chapter`
  守着，不需要也不该用卸载来清。
- 正文在版本跑完之后被改过（手改 / Agent 重写 / 常驻润色）时，明示这几版已过期，
  而不是让作者读完再点「采用」才撞上乐观锁冲突。
- **流式中的版本不给「采用」按钮**：想早退只能中止，不能早选（护住第 8 条的「沉浸读完
  整版再选」）。
- 常驻模式无观众，不做流式。

### 11. 正文写入来源新增 `llm-polish`

`ManuscriptRevisionSource` 增加 `llm-polish`，与 `author-save` / `agent-write` /
`agent-rewrite` / `revision-restore` 并列。润色采用走既有原子写入与乐观锁通道，不新造
写路径。

## 外审修复（2026-09-02，PR #72，9 条全部成立）

| 条目 | 修法 |
|---|---|
| 未验证的模型仍会真调 | `resolvePolishModel` 拒绝未验证条目 + 弹窗同款置灰。槽位是从整个池子里挑的，绕过了快捷切换器 `canSetPrimaryModel` 那道验证门 |
| 损坏的 `polish.json` 被下一次写入永久清空 | 读结果区分「缺文件」与「坏文件」；坏文件一律拒绝写回——空设置一旦落盘，旧章的分家标识没有任何来源可重建 |
| 项目写入绕过 `runProjectMutation` | 采用与常驻采用都包进同一道闸（只包采用，不占着锁跑模型） |
| 常驻会覆盖生成期间作者的手改 | `polishChapterOnce` 把「送去润色的那一份原稿」带出来当乐观锁基线。模型返回后重读磁盘等于把作者的改动当基线，锁形同虚设 |
| 新造人名不触发漂移 | **接受为已知盲区，不补开世界判据**。试过用「对白署名」（`X说 / X道` 前的 2-3 字）做开世界补充，两版都误报：贪婪匹配把「王五笑道」切成「王五笑」，改懒匹配后「此事不难说清」→「事不难」——中文没有词边界，正则在这件事上没有可用的误报边界。而**误报比漏报贵得多**：一次误报让常驻整章跳过正常润色，漏报只是少一道保险。兜底靠三件事：锚清单明写「不要凭空加入清单以外的人物」、试验模式有人在读、常驻的前提是配方已在试验阶段验证过。真要检测得上分词或模型，不属于确定性护栏这一层 |
| 常驻跑完 UI 不刷新 | 后台任务收尾广播 `standing-finished`，正文页据此重读设置与正文 |
| 「先不写」也会误润上一章 | 写作命令有「先不写」出口、run 照常结束；改判**这一章的正文是否在本次 run 之后才落盘**（fail-safe 方向：不确定就当没写） |
| 常驻没有超时 | `polishChapterOnce` 同样加 6 分钟 timer——后台没人盯着，挂住就是永远挂住，连「已跳过」都留不下 |
| 弹窗越过 Dialog 规范且窄窗不可用 | 补 `docs/design.md` §9.7 的「对比型弹窗」档（≤1320px + 必须窄窗降栏），偏离改为有据可依；界面加 `grid-cols-1 lg:grid-cols-3` |

**第二至四轮外审（同日，逐轮全部成立）**：

| 条目 | 修法 |
|---|---|
| 常驻跑完只刷横幅不刷正文 | 正文来自父组件的 artifact，收尾时一并 `onChanged` |
| 损坏保护只判 JSON 解析 | 补字段结构与 `version` 校验；结构坏掉或未来 v2 文件都拒绝写回 |
| `recover-write` 不触发常驻 / mtime 判据受草稿 rename 影响 | 两条写作路径都触发；判据改为「本次 run 期间登记过 `agent-write` 版本记录」，且**起止两头都判**——检查是异步旁路，只判起点会把下一轮很快写出的正文错认成自己的 |
| 润色版本随离开页面消失 | 清理曾挂在组件卸载上，实际是「离开这一页就丢」；改为只由丢弃 / 采用 / 发起新一轮清空，并按基线比对标示「已过期」 |
| 常驻提议每采用一版就弹 | 一本书只问一次（`standingPromptAnswered`）；Esc / 遮罩关闭不算回答 |
| 跨小说串数据 | 版本归属改判 `projectPath + chapter`；基线过期时禁用采用而不只是提示 |
| 丢弃 / 采用 / 再发一轮不取消上一轮 | 三条路径都先 `cancelAll` 再清状态；store 在 runId 为空的窗口只放行 `started`，旧 run 的增量与中止事件一律丢 |
| 成功态 toast | 全部去掉（design.md：Toast 不做操作确认），收场由内联横条承担 |
| 版本状态各处重复判断 | 收敛为 `derivePolishVersionView` 一处派生 + `isPolishVersionRunning` 一条谓词 |
| 采用后先等常驻提议框才取消其余版本 | 落盘成功即取消（框可能一直开着）；取消失败只记日志，不把已落盘的采用报成失败 |

**方法论记档**：①其中三条（乐观锁基线、闭世界盲区、「先不写」）都是**逻辑推演能发现、测试却全绿**的缺陷——原测试写的是「乐观锁失败 → 跳过」，但夹具用 `readOriginalText` 注入了不一致的基线，等于绕开了真实调用路径去验证一个假场景。**夹具替掉的正是被测的那条线时，绿灯毫无意义。**②「断言数据不是 DOM」再犯一次：`option.reason` 算了但从没渲染，而测试断言的是源码里有那句话。③进程级 zustand store 会跨测试文件泄漏：`standingVersion` 被 `reset()` 刻意不清，一个测试抬了它不复原，同进程后面挂载正文页的测试首帧就多触发一次刷新——单跑绿、全量红。

## Consequences

**得到**：作者第一次拥有「我要它这么写」的直接手段，且失败责任落在他自己的提示词上；
产品在文字风格这一层从「唯一供给方」退成「通道提供方」。引擎零改动，可随时整体下线。

**代价与已知风险**：

1. **最大风险不是效果差，是没人用**。B 定位 + 空模板，功能可能安静躺着无人问津。因此
   **必须埋使用率遥测**——要测的不是效果，是「有没有人真的写出第一条提示词」，这是判断
   「结构脚手架」这个引导方案成不成立的唯一证据。
2. **2026-07-27 的盲读结论仍然成立**：句子级润色改不动怪比喻与上下文不连贯。本功能不解决
   那两个症状，它解决的是「作者想自己动手时没有手」。若作者用它也润不出效果，那不是本
   功能失败，是那两个生成层病灶仍需回生成层修。
3. **旧章漂移采用后记忆与正文永久分家**（第 7 条），且无出口。长期解法是让
   `/sync-chapter-memory` 支持任意历史章（需真单章回滚 + 后续章节牵连处理），届时本条
   分支可收敛。
4. **交付必须真机 dogfood**，单测证明不了链路真的到达模型（既有教训：`definition.skills`
   eager 预加载单测全绿、真机实测不触发）。
