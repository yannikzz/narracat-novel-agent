# ADR-0038: 客户端版本号由人在 package.json 声明，不再从提交数派生

Status: Accepted

Date: 2026-08-30

Supersedes: [ADR-0006](0006-client-build-version-is-derived-at-build-time.md)

## Context

ADR-0006 定的规则是：客户端版本 = `<线前缀>.<release commit 提交数>`，由打包/发布链在打包时用
`git rev-list --count HEAD` 派生，`package.json.version` 只当作源码清单基础版本（长期是死值 `0.1.0`）。
当时要解决的问题是「把版本号写进 package.json 会自引用」——改 package.json 本身就是一个新提交，
提交数随即变化，committed 版本立刻过期。

那个问题是真的，但派生方案把版本号绑在了**「当前分支的历史有多长」**上，而不是**「这是第几次发布」**上。
两者在单分支线性开发下碰巧一致，一旦有分支、有 squash、有历史重写、有多平台，就分叉。

### 已经发生的事故

2026-08-30，Windows 适配 PR（#58）合并当日实测：

| 位置 | 提交数 | 派生版本 |
|---|---|---|
| `main` | 74 | `0.2.74` |
| `feat/windows-port`（CI 出包、已交付真机验收） | 92 | **`0.2.92`** |
| squash 合并后的 `main` | 75 | `0.2.75` |

产品主人机器上装的是 `0.2.92`。合并后主干只有 `0.2.75`，之后正式发版发 `0.2.76`、`0.2.77`……
在 electron-updater 眼里**全部低于**已安装版本，于是那台机器**收不到任何更新，且不报错、不提示**——
要等主干再累积 17 次提交才追得上。同一条更新链此前已因版本号问题踩过一次（测试包被自动更新静默换成
线上版，真机验收测到老引擎、日志毫无痕迹），只是方向相反。

### 派生方案的四个结构性缺陷

1. **跨分支不稳定**：同一份代码在两个分支上是两个版本号。
2. **合并策略会改变它**：本仓用 squash 合并，18 个提交压成 1 个，计数直接少 17。
3. **历史重写会重置它**：2026-08-04 干净历史重建后计数归零，撞上旧仓版本线，被迫把前缀从 `0.1`
   抬到 `0.2`（ADR-0006 的 Amendment）。那次是打补丁，不是修根因。
4. **多平台无法同号**：mac 包在本机打（要签名 + 公证，慢），Windows 包走 CI（5 分钟）。
   两条路径检出的提交数只要差一个，版本号就不同——而 ADR-0006 时代只有 mac，这个缺陷不存在。

第 4 条是本次的直接触发点：Windows 成为第二个分发平台后，「两平台同号」从锦上添花变成了发版的前提。

### 顺带一提

派生方案还有一个一直存在但没人当回事的问题：`0.2.92` 这个数字对用户和维护者都没有意义，
说明不了这是新增能力还是修了个错别字。而 `package.json` 里那个与真实版本无关的 `0.1.0`
会误导任何第一次读代码的人。

## Decision

**版本号的唯一真相源是 `package.json` 的 `version` 字段，由人在发版时显式决定。**

- 打包链、发布链、设置页「关于」全部读这一个值，两条取值路径（electron-builder
  `--config.extraMetadata.version` / vite 构建期 `define`）同源不变，只是源头从 git 计数换成 manifest。
- `NARRACAT_CLIENT_VERSION` 覆盖机制**原样保留**——测试包压过线上版本这个需求与本 ADR 正交，
  且那套机制已经过实战验证。
- 版本线起点定 **`0.3.0`**：必须同时超过线上最新正式版 `0.2.65` 与已交付真机的 `0.2.92`，
  两边用户才都能收到更新，一个都不掉队。抬 minor 而非继续在 `0.2.x` 上加数字，理由与
  ADR-0006 Amendment 相同——semver 下 `0.3.x` 恒大于任何 `0.2.x`，一次性了结，不必猜旧线数到了哪。
- 递进规矩：修 bug 走 patch（`0.3.1`）；有明显新能力走 minor（`0.4.0`）；`1.0.0` 留给正式公开发布。

### 关于 ADR-0006 那个「自引用」顾虑

它成立，但代价被高估了：改 `package.json` 的 version 确实产生一个新提交，然而**新方案里没有任何东西
依赖提交数**，所以「committed 版本立刻过期」这件事根本不会发生。自引用只在「版本必须等于提交数」
这条规则下才是问题——那条规则本身才是根因。

## Consequences

### 放弃了什么，拿什么补

派生方案唯一的真好处是**永不重复、永不忘记**。改成人来定之后这两件事都可能出错，故补两道闸：

1. **版本线不变量测试**（`scripts/client-version.test.mjs`）：`package.json.version` 必须严格大于
   `HIGHEST_SHIPPED_VERSION`（已发到用户手上的最高版本，当前 `0.2.92`）。手滑改小、忘了随发版更新，
   测试即红。这条替代了 ADR-0006 里「哪怕提交数只有 1 也要压过 `0.1.1930`」那条不变量，职责相同。
2. **发版前的重复版本闸**（`scripts/release.mjs`）：发布开始前检查 `v<version>` tag 是否已存在，
   存在即 fail-loud 并提示「是不是忘了 bump」。派生时代计数只增不减、天然不重复，改手动后这条必须补。

发版清单相应增加一步「决定并 bump 版本号」，位置在最前——它现在是发版的**输入**，不再是打包的副产品。

顺带补第三道（与版本号无关、但属同族的静默问题）：**发版必须显式声明覆盖平台**——
`release --with-win <目录>` 或 `--mac-only`，两个都不给直接炸。

「不给就只发 mac」这个默认在只有 mac 的时代是对的，Windows 成为正式分发平台后变成静默陷阱，
**而且后果比「少发一个包」重得多**：更新代理 Worker 把两个平台的清单**都**翻译成
`releases/latest/download/<清单名>`，所以一个只含单平台产物的 Release 一旦成为 latest，
另一个平台的清单查询直接 404——那条更新链就此断掉，直到下一次带上该平台产物的发布为止。
不是「停在上一版」，是从此收不到任何更新，且两端都没有报错。

**推论：一旦两个平台都有用户，每次发版都必须是双平台。** `--mac-only` 只为「Windows 尚未
发布过」的当下和 Windows CI 出包失败又必须紧急发 mac 修复的极端情况保留。

### OPS 校验的变化

`ops:check` 从「版本解析器存在且产出 `0.2.<提交数>`」改为「`package.json.version` 是合法三段 semver，
且版本解析器读到的值与之一致」。校验方一律用导出的 `CLIENT_VERSION_RE`，不要各自手写正则
（这条纪律沿用 ADR-0006）。

### 文件改名

`scripts/client-build-version.mjs` → `scripts/client-version.mjs`。「build version」这个名字在新方案下
名不副实——版本不再是构建的产物，而是构建的输入。`ops-check.mjs` 里那份需人工同步的文件清单同步更新。

### 不受影响的

产物命名、更新 feed 结构、Worker 反代路径、tag 格式（`v<version>`）、两平台产物进同一个 Release
的流程，全部不变——它们消费的一直是「一个版本号字符串」，不关心它从哪来。
