# ADR-0039: 匿名使用统计——先告知的默认开（informed opt-out），红线由代码机械执行

Status: Accepted

Date: 2026-08-30

## Context

到 0.3.x 为止，NarraCat 对"用户到底怎么用它"一无所知：全仓零埋点，唯一的用户信号是 GitHub issue
和用户群里的零星反馈。产品决策（哪个功能该投入、哪个该砍）全靠猜。

同时，这是一个格外不适合随手加埋点的产品：

- 用户是把**未发表稿件**交给我们的中文网文作者，稿件泄漏对他们是实质损失；
- 仓库 AGPL 公开，任何人可以逐行审代码——藏一个埋点域名被翻出来，信任一次性归零；
- 前车之鉴：Audacity 因加入遥测遭遇社区抵制并撤回；VS Code 的默认开遥测把一批用户推向 Zed。
  这两次翻车的共同点都不是"采集了什么"，而是**"没说清楚就采集"**。

ADR-0026 曾预留过 Sentry crash 上报（含"首启同意开关 + scrub 正文"），两年未落地。本 ADR 覆盖
它未竟的那部分，并把范围收窄到产品分析，明确不做自动堆栈捕获。

## Decision

### 一、要回答的问题（决定采集什么的上游）

**哪些功能没人用。** 判据不是"点击次数低"——那分不清"没价值 / 没被看见 / 用得少但离不开"。
最小可回答口径是每个模块的三个数：

| 数 | 来源 |
|---|---|
| 有机会用（分母） | `app_started` 的当日去重人数 |
| 用过一次 | 该模块 `feature_used` 的去重人数 |
| 用了第二次 | 该模块在**不同自然日**再次出现的人数（留存分析） |

第三个数才是"有没有价值"的真信号。

### 二、信任模型：informed opt-out

默认开，但**首启/升级时明确告知，一键可关**。选这一档而非"默认关"的理由与本 ADR 的目的直接相关：
默认关的同意率通常只有 10–30%，且愿意开的偏向重度/极客用户——他们恰恰最会用能力包、记忆星图这类
高级功能。用这样的样本决定"砍哪个功能"，会系统性高估高级功能的使用度。

配套四条硬承诺，缺一条则本决定失效：

1. 只传枚举值与分桶数字，不传任何文本；
2. 首启/升级一屏明说，不偷埋；
3. 设置里一个开关，立即生效；
4. 事件全清单公开在文档里，可逐条核对。

### 三、红线（不可协商）

**永不传输**：小说正文、章节标题、大纲、立项卡、角色设定、任何用户输入文本、API Key、
本机文件路径、小说名、小说题材标签。

题材标签是唯一被讨论后否决的灰区项：它与作品强相关且常是自由输入。已采纳的灰区三项是
模型 provider + 模型 ID、规模分桶、报错枚举码。

红线不靠"记得别写"，靠三道机械闸：

| 闸 | 位置 | 作用 |
|---|---|---|
| 类型 | `shared/types/telemetry.ts` | 事件与字段是枚举，新字段必须先进字典 |
| 客户端清洗 | `electron/main/telemetry/telemetry.ts` 的 `sanitizeEvent` | 白名单外的键丢弃；值超 64 字符或含换行 → 整条丢弃（枚举值不可能长这样，长了就说明夹带了文本） |
| 服务端清洗 | `workers/narracat-telemetry` | 同一份白名单再执行一次——**客户端被改过，正文也进不了 PostHog** |

### 四、数据归属：PostHog Cloud EU 免费版

免费额度 100 万事件/月（我们估计用不到 5%），漏斗/留存/分群开箱即用。选 EU 区而非默认美国区：
隐私叙事上 GDPR 管辖更好讲，功能完全一致。

自建 PostHog 被否（需 ClickHouse，一人团队运维负担重）；自造 CF Worker + 自建存储被否
（留存分析要现写 SQL，产品主人自己看不了数据，等于没有）。

### 五、传输：经自有域名反代

App 只认识 `telemetry.narracat.com`，Worker 转发到 PostHog。三个收益：

1. **中国可达性**——`eu.i.posthog.com` 在国内无保障；`*.narracat.com` 这条 CF 链路已在中国用户
   真机上跑通（0.3.0 更新链接通那次）。这也意味着"链路通不通"这个未知项被架构本身兜住了：
   收不到数据时改 Worker 即可，**不用发新版**。
2. **写入 Key 不进客户端**——Key 是 Worker secret，仓库和安装包里都没有。
3. **换供应商不用发版**。

子域名刻意叫 `telemetry`，**不采纳** PostHog 官方"起隐蔽名（`e`/`t`/`ingest`）躲广告拦截器"的建议：
桌面 app 躲拦截器收益近乎为零，被发现"藏埋点域名"的信任损失却是致命的。

### 六、粒度：模块级，全库六类事件

不按 130 个 IPC 动作各埋各的（字典巨大、必然漂移、结论淹没在噪声里），而是 16 个功能模块，
每模块每自然日最多一条。事件类型：`app_started` / `feature_used` / `chapter_write_started` /
`chapter_write_finished` / `error_occurred` / `telemetry_opt_out`。

`telemetry_opt_out`（关闭时发的最后一条）不是可选项：不知道关闭率就无法解释剩下的数据偏成什么样。

**接入方式**：在 IPC 装配处（`ipc/registry.ts` → `ipc/telemetry-tap.ts`）统一挂壳，业务代码零埋点。
归属表 `telemetry/ipc-modules.ts` 是唯一判断处，`ipc-modules.test.ts` 双向卡死——
新通道未判归属会红，表里有已删除通道也会红。

`null` 归属表示"显式不计入"，不是"还没想好"：读取与轮询类通道若计入，所有模块使用率会被抬到接近
100%，等于没测。

### 七、发送：批量发 + 落盘补发

攒够 20 条或 30 秒发一批；失败落盘，下次启动补发，上限 7 天 / 500 条。

不选"发不出去就丢"的原因不显眼但很脏：中国网络下会**系统性丢掉网络差的那批用户**的数据，
而"没数据"会被读成"没人用"——正好把要求的结论带偏。

队列文件是明文 JSON 且设置页给了"在文件夹中显示"入口。**不要改成二进制或加密**：
它是"透明"这句话的物证。

### 八、存量用户：升级后弹一次告知，默认开

不搞双重标准（存量默认关），也不静默开启。**告知屏确认前一个事件都不发**，闸门在
`isTelemetryAllowed`：判的是"已确认版本 >= 当前告知版本"。

实现上用独立的 `telemetryNoticeAckedVersion` 门控，**不复用 `introVersion`**——复用会逼存量用户
把五幕首启介绍重看一遍，为一屏告知付出的体验代价太大。

> **脚枪**：改告知屏文案（尤其新增采集项）必须 bump `CURRENT_TELEMETRY_NOTICE_VERSION`，
> 否则已确认过的用户永远看不到新口径，等于没告知，且没有任何报错。与 `CURRENT_INTRO_VERSION` 同款。

### 九、错误上报：只发自定义枚举码，不开自动捕获

不开 PostHog error tracking 的自动堆栈捕获。理由是它与红线正面冲突：模型报错文本常夹带正文片段，
堆栈常夹带本机路径。代价是意外崩溃只知道"崩了"不知道"崩在哪行"，修 bug 仍靠用户发日志——认这个代价。

### 十、身份：本机随机 UUID

`randomUUID()` 存 config，**不碰任何机器指纹 / MAC / 硬件号**，设置里可重置。代价是重装即断裂、
一人两机算两人；换来的是"我们永远无法反查到具体某个人"这句话在公开仓里站得住。

配置文件是用户可编辑的，故归一化时只接受 UUID 形态，手改成邮箱/机器名一律清空重生成。

### 十一、不引 SDK，直发 batch API

`posthog-node` 会自动附加 `$ip` / `$lib` / 自动采集属性——那样就无法用一个函数说清楚"我们到底发了什么"。
`buildWirePayload` 是可审计性的落点：读它一个函数即可确认字段一个不多。副产品是零新增依赖，
也绕开了 Electron 里装 PostHog SDK 的已知麻烦。

## Consequences

- 从下一版起可以回答"哪个模块没人用"，并在两个版本后据此做取舍。
- 多一个 Worker（约 130 行）与一条主进程链路要维护；埋点全链路 fail-safe，任何异常都不影响 App。
- 开发态默认不发（`transportEnabled()` 判 `app.isPackaged`），避免开发者自己的点击污染使用度数据。
- 数据出境：采集项全为匿名枚举，无法识别到自然人，不构成个人信息。

## 未闭合的未知项

1. **同意率会不会崩**。默认开是业界主流，但中文网文作者这个群体没有先例。关闭率若超 30%，
   样本重新有偏——这个数由 `telemetry_opt_out` 自己回答。
2. ~~**中国可达性未端到端验证**~~ → **2026-08-30 已闭合**。Worker 部署 + 域名绑定完成后端到端实测：
   GET → 405、空 batch → 400、伪造正文事件 → 400（服务端红线确实在转发前拦下）、
   `distinct_id` 非 UUID → 400；一条真实 `app_started` 经 `telemetry.narracat.com` 转发后
   在 PostHog EU 确认收到。
   > **测试事件留痕**：`distinct_id = 3f2504e0-4f89-41d3-9a0c-0305e82c3301`
   > （2026-08-30T15:35:16Z，`app_version=0.3.1`）是人工验证链路时发的，**不是真实用户**，
   > 分析时应排除。
   >
   > **顺带记一个设计上的钝角**：Worker 在 `POSTHOG_API_KEY` 未配置时返回 204（假装成功，
   > 避免我们的运维问题让用户机器反复重试）。代价是 **204 分不清「已转发」与「Key 没配、悄悄丢了」**——
   > 客户端侧这个取舍是对的，但它意味着**验证链路时不能只看响应码，必须去 PostHog 里眼见为实**。
3. **"砍功能"的阈值现在不定**。没有基线时定阈值是瞎定。收满两个版本数据后再定，
   届时补写进本 ADR 的修订。
